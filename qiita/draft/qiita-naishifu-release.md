## はじめに

ボーイとして週6・月240時間働いていた頃、開店前のルーティンは「全員にLINEを送る」ことだった。

担当の女の子10人にLINEを送っていたんですが、まぁーめんどくさいし**漏れる**んですよ。

「この単純作業、自動化したいな」と思ってアプリを作ってみました。

出勤リマインドLINEを自動化して**単純作業をゼロにする**ことを目的に、結果として**三方よし**の価値提供を目指しています。

### 提供する価値

**ボーイ側**
- 出勤リマインドLINEを自動化し、単純作業をゼロにする
- 仕事前から仕事のことを考えなくていい環境をつくる
- 本来の仕事（営業・接客）に集中できる

**女の子側**
- 毎回ボーイから確認LINEが来るプレッシャーがなくなる
- アプリ上で出勤報告できるので手間が減る

**店舗側**
- 欠勤の把握が早くなり当日の対応がスムーズになる
- ボーイが本来の仕事に集中できることで店舗全体のパフォーマンスが上がる

---

## ビジョン

業界のほとんどの店舗が出勤管理をタイムカード、女の子の出勤確認をLINEで行っており、**デジタル化が遅れている**。

ナイシフはその課題に正面から向き合い、**夜職業界に初めて本格的な出勤管理のDXをもたらすアプリ**を目指す。

### このアプリの動き

- ボーイがブラウザでシフト登録
- 当日朝、女の子のLINEに**自動でリマインド送信**
- 女の子は「出勤」「欠勤」を**LINEで1タップ返信**
- ボーイの管理画面に**リアルタイムで集計反映**

## 技術選定

### なぜ Next.js（App Router）？

個人開発で**フロントとAPIサーバーを別々に管理する余裕がない**。Next.js なら同じリポジトリでフロントエンドとAPI Routes（LINE Webhookなど）を共存できる。

App Router を選んだのは、**Server Components で初期表示の認証チェックをサーバー側で完結**させたかったから。LIFF の token 検証は Server Side で走らせると Client Side のコード量が減る。

### なぜ Supabase？

「店舗A の管理画面で店舗B のデータが見えたら**即座に契約解除レベルの事故**」になる SaaS。だから RLS（Row Level Security）でDBレベルで完全分離できる Supabase を選んだ。

```sql
-- 自店舗のシフトしか見えない
CREATE POLICY "store_isolation" ON shifts
  USING (store_id IN (SELECT store_id FROM staff WHERE auth.uid() = user_id));
```

アプリ側で「WHERE store_id = ?」を書き忘れても、**DB側で弾いてくれる安心感**が決め手。

### なぜ LINE LIFF？

ターゲットユーザー（女の子）は**LINE以外のアプリをほぼ使わない**。
- 専用アプリのインストール → 確実に挫折
- ブラウザでログイン → パスワード忘れ多発

LIFF（LINE内ブラウザ）なら**LINEの友達追加 = ログイン**が完結する。新規ユーザーの離脱率を最小化するための選定。

### なぜ Vercel + GitHub Actions？

- `git push` するだけで lint → test → build → deploy が自動実行
- テストが落ちたらデプロイされない = 安全網
- Vercel Cron が標準装備なので、**リマインド送信のスケジューラーを別途立てなくていい**

## 設計判断

### 1. 「店舗 × 女の子」の権限設計

3層構造で権限を分離:

| エンティティ | 権限 |
|---|---|
| 店舗（store） | 自店舗の全データを閲覧・編集 |
| 黒服（staff） | 所属店舗のデータを閲覧・編集 |
| 女の子（girls） | 自分のシフトのみ参照、出欠返信のみ可能 |

**なぜ:** マルチテナントSaaSで一番怖いのは「他店舗のデータ漏洩」。Supabase RLS で**コードバグでも漏洩しない設計**にした。

### 2. LINE連携の段階的導入

LINE未登録でもシフト管理単体は使える設計。

- まず**シフト登録機能だけ**で価値を出す
- LINE連携はオプション（QRコードで後から紐付け）
- 段階的に使い始められる導線

**なぜ:** 「LINE連携必須」にすると、最初の1人目の女の子に登録してもらう前に挫折する。**シフト管理だけでも価値がある状態**を先に作った。

### 3. UNIQUE制約 + 部分インデックス

`girls.line_user_id` に **「NULL は重複OK、値があれば重複NG」** の部分インデックスを設定。

```sql
CREATE UNIQUE INDEX girls_line_user_id_unique
  ON girls (line_user_id)
  WHERE line_user_id IS NOT NULL;
```

**なぜ:** 「同じLINEアカウントが複数の女の子に紐付く」事故を**DB側で物理的に防ぐ**。アプリ層のチェックだけだとレースコンディションで突破される。

### 4. 段階的リリース（MVP戦略）

1ヶ月を5つのMVPに分割:

| フェーズ | 内容 | 状態 |
|---|---|---|
| MVP1（Week1前半） | 基盤構築・認証（Next.js + Supabase + Vercel + 自動デプロイ） | 完了 |
| MVP2（Week1後半） | メンバー管理（女の子・黒服の登録・RLS設定） | 完了 |
| MVP3（Week2） | シフト登録・管理（CRUD + 出勤ステータス管理） | 完了 |
| MVP4（Week3） | **LINE連携・リマインド自動送信（最大の山場）** | 完了 |
| MVP5（Week4） | 仕上げ・リリース（UI整理・エラーハンドリング） | 完了 |

**どのフェーズで時間切れになっても動くプロダクトが残る設計。**

### 5. MVP4を「山場」と定義して逆算した

このアプリのコアバリューは「LINEで出欠確認が完結すること」。逆に言えば**MVP1〜3が遅れると、肝心のLINE連携に時間が残らない**。

だから MVP1〜3 は機能を最小限に絞った:
- 認証はメール/パスワードのみ（ソーシャルログインは後回し）
- 黒服管理画面は最低限のCRUD
- シフト登録はカレンダー連携なし、シンプルなフォーム

その代わり MVP4 に2週間相当の余裕を確保。結果、MVP4 で発見した**レースコンディションバグ（同じLINE userId が4人に紐付く）をじっくり潰す時間が取れた**。

**「実装中に見つかったバグを潰す時間まで含めて見積もる」** ことが MVP 戦略の本質だと実感した。

## 学び・気づき

### 1. UNIQUE制約バグを実機テストで発見

LINE連携の通し確認をしていたら、**同じLINEアカウントが4人の女の子に紐付いていた**ことに気づいた。

原因は「`SELECT` で重複チェック → なければ `INSERT`」というアプリ層の実装。**チェックと書き込みの間に他リクエストが入り込めるレースコンディション**だった。

DB側で UNIQUE 制約を効かせれば物理的に重複を防げる。**「アプリ層のチェックは保険、DB制約が本番」** と実感した瞬間だった。

### 2. テストは最強の味方

全機能に対して **77のテスト** を書いた。
Jest + React Testing Library で、UI操作とAPIコールを全部モックして検証。

`pnpm test` を実行したら、**5秒以内ですべてPASS**。

手動だと毎回30分かかる確認が、コマンド1つで完了。リファクタする時の心理的安全性が圧倒的に違う。

### 3. MVP分割が「途中で力尽きない」を実現した

正直、最初は「1ヶ月で本当にリリースできるのか？」と不安だった。

でも MVP を5つに分けて、**毎週末に「動くもの」が必ず手元にある状態**を作ったら、モチベーションが切れなかった。

- MVP2 を終えた時点で「メンバー管理アプリ」として動く
- MVP3 を終えた時点で「シフト管理アプリ」として動く
- MVP4 で LINE 連携が乗って「これがやりたかったやつ」が完成

**段階的に動くものが残る設計**は、個人開発の精神安定剤だった。

### 4. 完璧主義を捨てる勇気

MVPを5つに分割して回す中で、「ここもっと作り込みたい」と何度も思った。

でも**「動くものを世に出す」が最優先**。完璧を目指して未公開のままより、半端でも公開した方が圧倒的にフィードバックが得られる。実際、初リリース後に発見したバグの方が、机上で想定したバグより遥かに価値があった。

**個人開発で挫折する最大の理由は完璧主義。** 「とりあえず出す」を選べた自分を褒めたい。
